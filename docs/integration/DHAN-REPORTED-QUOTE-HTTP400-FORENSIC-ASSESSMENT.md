# Reported Reliance quote HTTP 200 / IPD vendor HTTP 400 — forensic assessment

**Scope:** the operator-reported 15 and 18 November 2026 observations. **Source baseline:** IPD `bfd83216f738a8cb6ad893f57934a582902bbdac`; assessment work is on `arena/78c812f4-iips-production-market-data`. **Verdict:** **root cause not established.** No credential, DPAPI carrier, Windows process, vendor request, or vendor response body was available to this investigation. In particular, this report does not reinterpret either of the two independent HTTP 200 results as a failed authentication.

## 3. End-to-end request and status trace (source-derived, not a packet capture)

1. [Loopback HTTP server](../../src/providers/dhan/dhan_market_data_http.ts), lines 363–374 and 529–556: `POST /v1/quotes` authenticates its **local transport bearer** and validates a canonical `companyId` / security identity before calling the service. A failure here would be a local `401` or `400`, not the observed vendor-status-bearing failure.
2. [Service](../../src/providers/dhan/dhan_market_data_service.ts), lines 761–826: exact `companyId` + segment + ISIN + series resolution precedes a provider call; the default segment is `NSE_EQ`. A missing/ambiguous row fails locally. With the *checked-in* Reliance row and identity, [source](../../src/providers/dhan/dhan_market_data_source.ts), lines 87–125, sends one `NSE_EQ` instrument ID `2885` to the client.
3. [Client](../../src/providers/dhan/dhan_api_client.ts), lines 239–250 and 296–425: for that mapping it serializes `{"NSE_EQ":["2885"]}`, checks expiry, resolves **both** secrets per request, and constructs `POST ${baseUrl}/marketfeed/quote`. The **default**, not a measured Windows value, is `https://api.dhan.co/v2/marketfeed/quote`; JSON `Content-Type` and `Accept` are set alongside separate `access-token` and `client-id` headers. The local bearer is **not** forwarded to Dhan. Configuration captures the base URL, timeout and SecretRef metadata at daemon startup ([config](../../src/providers/dhan/dhan_config.ts), lines 34–51, 120–125; [daemon](../../src/providers/dhan/dhan_local_daemon.ts), lines 446–535), whereas the resolver reads carrier records for each request ([resolver](../../src/providers/dhan/dhan_local_vault_resolver.ts), lines 307–369). `PRESENT_OK` and startup readiness say nothing about equality with a separately used value.
4. [HTTPS transport](../../src/providers/dhan/dhan_server_egress.ts), lines 53–125: enforces HTTPS/origin/path-prefix, no URL credentials/query, TLS verification not disabled, `redirect: 'error'`, bounded `fetch`; reads `{status, bodyText}`. A returned HTTP status means an HTTP response was received along this path; it does not prove exact final wire bytes at Dhan, rule out an intermediary, or identify its application-level reason.
5. [Status map](../../src/providers/dhan/dhan_api_client.ts), lines 451–475 and 722–740: for **400**, `mapHttpStatus` returns `HTTP_ERROR` with `httpStatus: 400` **before** parsing `bodyText`. Only `401`/`403` map to `AUTHENTICATION_FAILURE`. A 400 does **not** increment the auth-failure latch ([recorder](../../src/providers/dhan/dhan_provider_state_recorder.ts), lines 255–292); `withBoundedRetry` does **not** automatically retry an HTTP 400 ([controls](../../src/providers/dhan/dhan_operational_controls.ts), lines 303–339, 392–441). Two reported 400 responses are consistent with the two operator-initiated IPD attempts, not evidence of an automatic retry.
6. The failure goes through the source/refresh outcome ([source](../../src/providers/dhan/dhan_market_data_source.ts), lines 120–126; [service](../../src/providers/dhan/dhan_market_data_service.ts), lines 725–735 and 795–826) to the [daemon](../../src/providers/dhan/dhan_market_data_http.ts), lines 559–581. Non-rate-limited provider failures become local **502**. Only the **numeric** vendor status is projected as `vendorHttpStatus: 400`; the consumer's `httpStatus` is **502** ([consumer](../../src/providers/dhan/dhan_market_data_http.ts), lines 625–656). These are different HTTP hops, not contradictory measurements.

A 400 alone is **not** a documented vendor authentication verdict. IPD deliberately labels it `HTTP_ERROR`; that label also does not prove *which* request field the responder objected to.

## 5. Vendor-error detail safety and limits

The HTTPS transport briefly holds the raw response text, but `executeJsonPost` returns on non-2xx **without parsing or retaining it**. No past body can be reconstructed from a later `/v1/health` or `/v1/diagnostics` read. Blindly logging/returning vendor error text, enabling unredacted HTTP traces or capturing request headers could reflect tokens or store locations and would violate the current D-7 disclosure discipline ([policy](DHAN-D7-PROVIDER-STATE-MODEL-AND-DIAGNOSTICS-POLICY-2026-11-12.md), §§3–5). **No such change is proposed.** A future, separately governed change, *if justified after passive evidence*, would need an explicit disclosure-policy decision and tests for a narrowly allowlisted, bounded derived category with unknown fields discarded; never raw body or raw headers. It cannot recover the two already-discarded bodies.
