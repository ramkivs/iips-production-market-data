# Reported Reliance quote HTTP 200 / IPD vendor HTTP 400 — forensic assessment

**Scope:** the operator-reported 15 and 18 November 2026 observations. **Source baseline:** IPD `bfd83216f738a8cb6ad893f57934a582902bbdac`; assessment work is on `arena/78c812f4-iips-production-market-data`. **Verdict:** **root cause not established.** No credential, DPAPI carrier, Windows process, vendor request, or vendor response body was available to this investigation. In particular, this report does not reinterpret either of the two independent HTTP 200 results as a failed authentication.

## 1. Evidence, with its limits

| Evidence | Established | Does **not** establish |
| --- | --- | --- |
| 15 November IPD Reliance NSE quote HTTP 200 (operator report) | An earlier IPD quote reportedly succeeded. | The original request/response, its payload, its loaded mapping, or the exact execution commit. No historical source tree is attributed to that run. |
| 18 November independent Reliance `NSE_EQ` / `2885` quote HTTP 200 **twice**, with the **same intended** Dhan client ID and token (operator report) | The intended credential pair worked for both independent requests under those requests' conditions. This is strong contrary evidence to a blanket assertion that that pair was unusable or that Market Quote access categorically did not exist. | The daemon's actual resolved credential values; byte-for-byte equality of the independent script's request with IPD's outbound request; a vendor guarantee that all future requests will be accepted. |
| IPD Windows run pinned to `bfd83216…`, DPAPI CLI `PRESENT_OK` for both roles, startup `CREDENTIALS_RESOLVED`, `IPD_SERVER_HTTPS`, `4,680` mappings (operator report) | Local carrier readiness, enabled outbound transport and a count at startup. | Vendor acceptance, equality with the independently used pair, the exact mapping row selected, the actually loaded JS files/daemon PID/CWD, or absence of runtime overrides. |
| IPD returned local HTTP **502**, `HTTP_ERROR`, `vendorHttpStatus: 400` twice; the second failure persisted after re-entry of the same existing token and DPAPI verify (operator report) | The IPD path attributed a **400** to an outbound HTTP response, then projected it through a separate local **502**. Re-entry/verification did not change that observation. | Why the HTTP responder returned 400, that Dhan rejected the *intended* credentials, or that a different token should be provisioned. |

The evidence does **not** support a token-renewal, subscription, instrument-mapping, runtime, or code-change root-cause claim. Two independent successes must remain in the causal analysis. Conversely, saying that the intended credentials were the same is not an in-process measurement of the values that IPD read and sent.

## 2. Git/source lineage, mapping, and compiled image

`git fetch --unshallow origin` and an explicit read-only fetch of historical candidate `8bbc299620bf4e88bd5f57f3f784b6894d99c3c9` made the lineage comparable. `8bbc299` is a **13 November W-06 reference tree**, not a proven 15 November execution commit. It was not on the then-current `main`; the DPAPI workflow was brought forward via `8d68edbfa24dcd080fff67f8ba86c19a076ab85e`, then merged as PR #174 at `bfd83216` on 17 November. The 15 November `main` lineage had a separate P7 manifest update; neither that fact nor any commit timestamp identifies the machine's running image on the date of the reported success.

Read-only comparison of `8bbc299` with `bfd83216`:

- `dhan_server_egress.ts`, `dhan_instrument_map.ts`, and `dhan_dpapi_vault_backend.ts` have **identical Git blobs** at both revisions. The quote serializer, POST URL concatenation, credential-header names and `400 → HTTP_ERROR` status mapping remain in `dhan_api_client.ts`; W-08/W-09 added state recording/probing, counters and an authentication latch, not a demonstrated quote-wire change. The W-06 strict-UTC expiry check is present in the reference and the baseline. The vault resolver's functional resolution path is unchanged in the comparison; its diff is comments/readiness text. The daemon's functional diff is the sanitized backend ID in startup diagnostics. W-07–W-10 introduced health/diagnostic/verification surfaces; this is **not** evidence of what compiled code ran on Windows.
- The P7 manifest changed from **596 records / 96 qualified** in `8bbc299` to **5,180 records / 4,680 qualified** in the checked-in 15 November update and at `bfd83216`. In **both** compared revisions, Reliance has exactly one qualified NSE row: `EQ_RELIANCE_IN`, `ISIN:INE002A01018:EQ`, `NSE_EQ`, Dhan ID `2885`; the BSE row remains `ISIN:INE002A01018:A`, `BSE_EQ`, `500325`. This rebuts an assertion that a *checked-in change to that specific row* caused the difference; it does **not** prove the daemon loaded that file or picked that row on the failing requests. The daemon searches `process.cwd()` **first** for the manifest, then locations relative to its compiled module; an injected manifest path is also available to controlled callers ([daemon loader](../../src/providers/dhan/dhan_local_daemon.ts), lines 275–319).
- `package.json` starts `node dist/src/providers/dhan/dhan_local_daemon.js`; `npm run build:tsc` runs `prebuild:tsc`, which removes stale runtime output before `tsc`. This cleanup was added in the restoration. **Arena's** fresh build from the pinned source with Node 22.22.3 / TypeScript 5.9.3 succeeded and the compiled quote client contains the described request and status mapping. **The incident host's `dist/`, build transcript, running PID and module image were not supplied.** A successful clean build *here* cannot prove what was loaded by an already-running Windows process. The earlier orphaned-`dist` ESM-link incident addressed by PR #174 was a different failure; it is not an explanation of this vendor HTTP response.

## 3. End-to-end request and status trace (source-derived, not a packet capture)

1. [Loopback HTTP server](../../src/providers/dhan/dhan_market_data_http.ts), lines 363–374 and 529–556: `POST /v1/quotes` authenticates its **local transport bearer** and validates a canonical `companyId` / security identity before calling the service. A failure here would be a local `401` or `400`, not the observed vendor-status-bearing failure.
2. [Service](../../src/providers/dhan/dhan_market_data_service.ts), lines 761–826: exact `companyId` + segment + ISIN + series resolution precedes a provider call; the default segment is `NSE_EQ`. A missing/ambiguous row fails locally. With the *checked-in* Reliance row and identity, [source](../../src/providers/dhan/dhan_market_data_source.ts), lines 87–125, sends one `NSE_EQ` instrument ID `2885` to the client.
3. [Client](../../src/providers/dhan/dhan_api_client.ts), lines 239–250 and 296–425: for that mapping it serializes `{"NSE_EQ":["2885"]}`, checks expiry, resolves **both** secrets per request, and constructs `POST ${baseUrl}/marketfeed/quote`. The **default**, not a measured Windows value, is `https://api.dhan.co/v2/marketfeed/quote`; JSON `Content-Type` and `Accept` are set alongside separate `access-token` and `client-id` headers. The local bearer is **not** forwarded to Dhan. Configuration captures the base URL, timeout and SecretRef metadata at daemon startup ([config](../../src/providers/dhan/dhan_config.ts), lines 34–51, 120–125; [daemon](../../src/providers/dhan/dhan_local_daemon.ts), lines 446–535), whereas the resolver reads carrier records for each request ([resolver](../../src/providers/dhan/dhan_local_vault_resolver.ts), lines 307–369). `PRESENT_OK` and startup readiness say nothing about equality with a separately used value.
4. [HTTPS transport](../../src/providers/dhan/dhan_server_egress.ts), lines 53–125: enforces HTTPS/origin/path-prefix, no URL credentials/query, TLS verification not disabled, `redirect: 'error'`, bounded `fetch`; reads `{status, bodyText}`. A returned HTTP status means an HTTP response was received along this path; it does not prove exact final wire bytes at Dhan, rule out an intermediary, or identify its application-level reason.
5. [Status map](../../src/providers/dhan/dhan_api_client.ts), lines 451–475 and 722–740: for **400**, `mapHttpStatus` returns `HTTP_ERROR` with `httpStatus: 400` **before** parsing `bodyText`. Only `401`/`403` map to `AUTHENTICATION_FAILURE`. A 400 does **not** increment the auth-failure latch ([recorder](../../src/providers/dhan/dhan_provider_state_recorder.ts), lines 255–292); `withBoundedRetry` does **not** automatically retry an HTTP 400 ([controls](../../src/providers/dhan/dhan_operational_controls.ts), lines 303–339, 392–441). Two reported 400 responses are consistent with the two operator-initiated IPD attempts, not evidence of an automatic retry.
6. The failure goes through the source/refresh outcome ([source](../../src/providers/dhan/dhan_market_data_source.ts), lines 120–126; [service](../../src/providers/dhan/dhan_market_data_service.ts), lines 725–735 and 795–826) to the [daemon](../../src/providers/dhan/dhan_market_data_http.ts), lines 559–581. Non-rate-limited provider failures become local **502**. Only the **numeric** vendor status is projected as `vendorHttpStatus: 400`; the consumer's `httpStatus` is **502** ([consumer](../../src/providers/dhan/dhan_market_data_http.ts), lines 625–656). These are different HTTP hops, not contradictory measurements.

A 400 alone is **not** a documented vendor authentication verdict. IPD deliberately labels it `HTTP_ERROR`; that label also does not prove *which* request field the responder objected to.

Potential explanations to **test, not assert**: (a) the running process emitted a different body, endpoint or set of headers than the independently successful requests; (b) its resolved pair differed despite the same intent and successful local DPAPI checks; (c) an override, different manifest due to CWD, or stale/different process image changed the execution path; (d) an HTTP intermediary or vendor-side validation/context returned 400 despite other successful quotes. The existing results alone do not rank or select these. A local bearer mismatch, failed exact-identity preflight, unavailable vault, DNS/TLS failure or local request-budget refusal by itself would produce a **different** code/status or no vendor 400; do not conflate those paths with the observed response.

## 5. Vendor-error detail safety and limits

The HTTPS transport briefly holds the raw response text, but `executeJsonPost` returns on non-2xx **without parsing or retaining it**. No past body can be reconstructed from a later `/v1/health` or `/v1/diagnostics` read. Blindly logging/returning vendor error text, enabling unredacted HTTP traces or capturing request headers could reflect tokens or store locations and would violate the current D-7 disclosure discipline ([policy](DHAN-D7-PROVIDER-STATE-MODEL-AND-DIAGNOSTICS-POLICY-2026-11-12.md), §§3–5). **No such change is proposed.** A future, separately governed change, *if justified after passive evidence*, would need an explicit disclosure-policy decision and tests for a narrowly allowlisted, bounded derived category with unknown fields discarded; never raw body or raw headers. It cannot recover the two already-discarded bodies.

## 6. Safe operator diagnostic and next action

A standalone [offline-first diagnostic](../../scripts/diagnose-dhan-quote-http400.mjs) is supplied. It is **not** a replacement for, or modification of, the existing Windows execution script. **Do not** change that script's commit pin, clean-tree guard, credentials, expiry, request, or execution sequence. Download/copy the diagnostic to a location **outside** the original pinned repository (otherwise its clean-tree guard fails). Do not checkout this assessment branch in the incident tree merely to obtain the diagnostic. Run as the ordinary authorized operator, not on Arena, with Node 22 and the **already installed** toolchain in the pinned tree. Use a separate terminal only to collect evidence; no rebuild of the live `dist/`, credential operation, process stop, or vendor call is required.

```powershell
# Replace the two path placeholders with existing paths. No credentials in arguments.
$repo = '<existing clean, commit-pinned IPD checkout>'
$diagnostic = '<copy of diagnose-dhan-quote-http400.mjs outside the checkout>'
$argsForDiagnostic = @('--repo', $repo, '--port', '8791')
# Only if these were recorded in the ORIGINAL launch/session:
# $argsForDiagnostic += @('--pid', '<recorded daemon PID>', '--launch-cwd', '<recorded original launch CWD>')
node $diagnostic @argsForDiagnostic
```

If PID or *original* CWD was not retained, omit the corresponding option rather than substitute the current shell's PID/CWD. If the operator configured a different daemon port, use that approved port, not an arbitrary discovery target. **Default mode sends no HTTP request of any kind**: it checks exact Git HEAD/tree and clean status (no dirty filenames printed), compiles into a short-lived **temporary folder outside the repo** to compare **all** on-disk runtime JS against a fresh local emit (without touching `dist/`), checks process start time/executable/entrypoint/PID/loopback listener when available, classifies **this shell's** config/strict expiry without printing values or reference locations, and runs a synthetic *in-memory* Reliance quote with a fake resolver and fake transport to witness method/endpoint/header **names**/body and the 400 mapping. The `credentialEquality` field deliberately remains `UNPROVEN_NOT_INSPECTED`. A compile match establishes *current disk* parity, not what a pre-existing process already loaded; the script reports whether the entrypoint disk file changed after process start. Windows process CWD is **not** introspected: an original-launch CWD is an operator attestation, explicitly labelled as such.

**Optional, no-vendor status step:** only with the operator's approval and the existing **local IPC bearer already present in that shell**, append `--read-local-status` to the same command. It first requires matching pin/clean tree, fresh build parity, entrypoint/PID/loopback ownership and build-before-process-start. Then it performs only direct, bounded `GET /v1/health` and `GET /v1/diagnostics` on that verified loopback address. It does **not** follow redirects, send a quote, call `/v1/connection/verify` (whose default mode is a **live vendor probe**), persist the bearer, or expose raw response bodies. If a prerequisite fails, it returns `BLOCKED_*` (or `REFUSED_*` for the pinned-tree guard) and sends no bearer. Health and diagnostics are observational; a `CREDENTIALS_RESOLVED` value remains local readiness, not vendor acceptance. **No vendor quote is authorized by this diagnostic.**

The **next operator action** is to supply the resulting **sanitized diagnostic JSON** (after normal local review), the **already-existing** successful independent script's method, endpoint, header *names*, JSON content type/accept, `NSE_EQ`/`2885` body and HTTP client/transport metadata **without header values**, plus any contemporaneous 15 November execution commit/manifest/build record if one exists. Do not repeat the two successful requests or paste secrets, environment dumps, carrier contents, process command lines, raw vendor bodies or token fingerprints. Compare these safe fields to §3, marking any unrecorded item **unknown**, not equal. If exact daemon-resolved credential equality becomes necessary after that comparison, it requires separate authority and an operator-controlled **in-process, memory-only boolean comparison at the send boundary**; no such credential-reading capability is shipped or requested here. A further live quote, if ever justified, is **at most one** and requires explicit new operator authorization; neither this assessment nor the tool initiates one.
