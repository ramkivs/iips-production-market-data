## B. Security identity and fundamental-data assessment

### Identity

**VERIFIED COMPLETE — bounded identity resolution.** IPD's offline search yields candidates, not qualification. Exact resolve requires company, exchange and `ISIN:<isin>:<series>`; qualification uses ISIN/exchange and fails closed for ambiguity. Master `lastVerifiedAt` is evidence of verification, not an established freshness guarantee (`IPD:docs/IPD-P4-IDENTITY-HTTP.md`). No network/provider credentials are required for identity operations once the daemon is admitted, but a running, configured daemon and applicable registry are not demonstrated here.

IRR has a separate issuer/security/listing resolver over a content-addressed eligible roster, listing map and corporate actions (`IRR:iips-platform/src/investment/identity/sources.ts:1-15`). It rejects sector-reference IDs as identities; exact ISIN precedes exchange+symbol, dated listing windows matter, and reused symbols or multiple securities can be ambiguous (`IRR:iips-platform/src/investment/identity/resolver.ts:175-230,260-320,340-420`). Roster issuer records carry sector and subsegment; absent classification can be `UNCLASSIFIED` (`identity/sources.ts:191`), not an independently verified current sector fact. IRR IID security IDs and IPD D114 identities are different contracts: joining them requires explicit, verified mapping and listing/series evidence.

**OUTSTANDING INVESTIGATION:** exact current portfolio coverage and per-row issuer mapping are unknown. A successful IPD security qualification does not establish an IRR issuer binding, dataset coverage, provider entitlement, a current exchange listing, or usable financials. `IRR:frontend/server/investment/coverage-transport.ts:1-15,70-95` deliberately fails the identity total if required observation sources are unavailable. The separate investment-coverage endpoint can still describe dataset coverage when identity sources are absent, disclosing the identity dependency instead of asserting it.

### Financial inputs, lineage and missingness

- **VERIFIED COMPLETE — available mechanism:** IID-0 reads an operator-supplied local dataset via `IRR:iips-platform/src/investment/port/localSnapshotStore.ts:1-12,35-45,120+`; `ingestion/writer.ts` verifies file and content digests. `fundamentals/manifest.ts:1-10,36-68,105-145` records content-addressed `datasetVersion`, file hashes, provider/license text, coverage, dataset `dataAsOf`, `knownAsOf`, and `lastImportAt`. `lastImportAt` is excluded from the content identity; a newer import timestamp does not mean newer financial periods. At build, dataset `dataAsOf` is the latest period end across the dataset, not necessarily the subject issuer's period; `knownAsOf` is the supplied import clock when periods exist.
- `IRR:iips-platform/src/investment/fundamentals/types.ts:15-75` models issuer sector, security, exchange/listing/series/effective dates, period start/end, scope, as-filed/restated basis, `filedAt`/filing reference, price `asOf`, source and adjustment. A stored dataset price is not automatically a live IPD quote. `assessment/periods.ts:1-16,60-85` separates scope, restatements, discrete quarters and TTM.
- `IRR:iips-platform/src/investment/coverage/measure.ts:1-12,60-105` measures a sector/method only when inputs exist; missing or unvalidated mandatory data yields withheld/unmeasured. `identity/coverage.ts:100-145` separates financial from identity coverage and labels data synthetic, operator-supplied or none. Its class is inferred from manifest text, not independent proof of source approval. In `IRR:frontend/server/investment/cli/generate-investment-artifacts.ts:325-350`, the classification `APPROVED_LOCAL_INGESTION` is assigned for non-synthetic provider strings; **do not treat that label alone as evidence of external authorization or entitlement**.
- `IRR:iips-platform/src/investment/contracts/observation.ts:1-42,62-145` distinguishes reported zero, source-declared nil, missing, unavailable, unmapped and not computable; nil may enter only explicitly authorized aggregations. A value is not zero merely because it is missing. `IRR:iips-platform/src/investment/assessment/engine.ts:215-235` evaluates price and statement vintage; unavailable values and policies limit results.
- **Verified evidence, not user coverage:** `IRR:frontend/server/investment/cli/realIssuerValidation.test.ts:1-8,31-80` references an operator-supplied Infosys disclosure evidence set and regression tests; test input is not a live feed or evidence that the user's holdings are covered. `IRR:docs/integration/IID-P6A-RUNTIME-DEPENDENCY-ASSESSMENT-2026-11-09.md` records an isolated earlier sandbox with fixture identity and absent dataset, not the user's host today. Those real-issuer tests were inspected, not rerun; the separate 14-test IPD read-contract run is described in section K.
- **OUTSTANDING INVESTIGATION / EXTERNAL DEPENDENCY:** authoritative production-excluded data provenance, rights, source-level timestamp and per-holding sector/method/period coverage must be measured on the intended non-production host. Dataset presence, a manifest label, a resolved identity or a fixture success is not sufficient. CLI `knownAsOf: manifest.knownAsOf ?? generatedAt` (`generate-investment-artifacts.ts:398-415`) is a fallback clock in that path; it must not be relabeled as proof of when a source was actually known. Investment coverage adapter synthesizes its report `generatedAt` as `asOf` midnight (`IRR:iips-platform/src/investment/identity/runtime.ts`, `investmentCoverageFromLocalDataset`); do not represent that value as an observed wall-clock execution time.

## D. Reports and IID persistence audit

### NP-06 / NP-04

**VERIFIED COMPLETE / VERIFIED — NO CHANGE REQUIRED:** `IRR:frontend/server/reports/persistence.ts:1-20,90-145,190+` validates canonical content and delegates to the separately pinned NP-04 port; it does not create a Reports database or mint NP-04 instance IDs. `reportKey` is derived from canonical chain-identifying members; `reportId` is a distinct persisted instance. NP-04 returns artifact version and supersession linkage. Two independent `persistNew` calls with identical content can produce separate instances; an append is not a new store. `IRR:frontend/server/reports-transport.ts:38-46,180-294` exposes list, create, detail, append and supersession routes with owner resolution and fail-closed persistence; the Reports **UI** is read-only, while the server has guarded POST routes. The separate operator reference-report producer reads `computeCertifiedPlatform` and uses `new Date().toISOString()` as generation time (`IRR:frontend/server/reports/persist-real-reports.ts:1-19,171-196`): the report is newly generated over frozen inputs, not newly observed market data.

`IRR:frontend/server/reports/artifact.ts` and `persistence-port.ts:54-87` retain report type, portfolio/scope, schema, `generatedAt`, canonical payload, provenance and NP-04 instance/version fields. There is no demonstrated universal mandatory `sourcePortfolioRevision`, quote time or dataset vintage for every generic report type. A `portfolioId` may be a scope token for IID, not an actual portfolio. **IMPLEMENTATION REQUIREMENT:** define per-report source lineage for any new current-portfolio producer and fail closed when required evidence is missing; do not retroactively invent fields on historical artifacts.

### Assessment chain

`IRR:frontend/server/investment/cli/generate-investment-artifacts.ts:1-25,325-415,520-600` reads the verified dataset and identity source, evaluates the issuer via `assessCompany`, composes and validates, compares against the chain, persists through existing service if needed, and rereads. This is an operator path; `IRR:frontend/server/investment/investment-transport.ts:138-176,248-330` GET/HEAD serves a validated stored head or selected version, not a new assessment. Owner/persistence absence is 503, absent chain/version 404; there is no replacement store.

`IRR:frontend/server/investment/assessmentComposition.ts:16-30,142-150,213-217,260-290` records payload and input digests, model/policy, dataset/content digest, `dataAsOf`, `knownAsOf`, and generation time. Stable parameters include schema, model/policy, statement scope, reporting currency and fiscal-year end. A changed stable parameter can change report key/chain identity; therefore do not promise every possible methodology/scope change remains on one chain without checking the chain lookup rules. Dataset and volatile values are deliberately not stable chain members. `investmentArtifacts.ts:524-640,697-815` uses substantive identity for clock-only versus content changes, validates chain membership and stored payloads, and can avoid writing unchanged observations. `INPUT_CHANGED_CONTENT_IDENTICAL` explicitly may leave the new input digest unpersisted; do not assume every attempted reassessment is a new durable version.

### Holding disposition and history

`IRR:frontend/server/investment/dispositionService.ts:149-205` composes through the same artifact service. `dispositionComposition.ts:125-152,224-257` binds subject scope, assessment references/digests, dataset/as-of, model/policy, limits and optional `portfolioRevision`. `iips-platform/src/investment/disposition/types.ts:173,216-228` records revision and dataset metadata. Holding and candidate scopes differ; nullable revision means absent evidence, not revision zero. `IRR:frontend/server/investment/disposition-transport.ts` is the read surface, not a broker execution service.

`IRR:frontend/server/investment/change-transport.ts:1-22,37-62` performs GET/HEAD comparisons of stored company versions; comparisons produced on read are not themselves persisted. `changeService.ts:1-15,43-48,210-297` can also reconcile stored boundary reports via an operator/service path with explicit coverage and idempotency. Exact attribution requires reproducible versions and matching model/policy; model-build digest and platform commit are explicitly unavailable, not reconstructed. `changeComposition.ts:217-260` sets a change report provenance `dataAsOf` and `knownAsOf` to the **explained version's generated date**, rather than copying the original financial data-as-of: treat those particular fields as a composition convention and inspect the underlying versions for actual data vintage; do not advertise them as the source observation dates.

### Staleness conclusion

A valid head means latest **persisted** artifact in its chain, not necessarily current holdings, price, filings, policy, identity or model. GET handlers read stored versions, so a source change does not itself demonstrate an updated assessment, disposition, or report. Disposition may record a portfolio revision but this review did not find a universal read-time comparison of the stored revision to IPD's current revision across all report paths. Assessments record data/policy freshness at calculation time; those facts can age afterward. **IMPLEMENTATION REQUIREMENT:** define revision/dataset/identity/model/quote comparisons and `current`, `stale`, `unknown`, `unavailable` disclosures without mutating old artifacts; use existing immutable chains. Whether and how a new version is produced is separately governed—no scheduler or automated refresh is authorized here.
