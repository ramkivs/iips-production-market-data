## 4. DOM execution of the real application

Because no browser binary is available, the **real client entry** (`frontend/src/main.tsx`) was
built in development mode (`import.meta.env.DEV === true`) as a single classic script and
executed inside **jsdom** at `http://localhost:5173/dev/dhan-d2?scenario=…`. This runs the
genuine application: `BrowserRouter` → `SessionProvider` → `App` → `AppShell` → the lazy
development surface, including React effects and the asynchronous harness. Build config and
runner live outside the repository (`/tmp`), so no verification tooling entered the codebase.

Captured DOM per scenario: `dom-current.html`, `dom-stale.html`, `dom-unavailable.html`
(full rendered markup) and `dom-current.json`, `dom-stale.json`, `dom-unavailable.json`
(extracted assertions + every table, console message and attempted network call).

## 7. Limitations

1. No browser screenshot could be captured (no Chromium in the sandbox, browser download
   endpoint unreachable). The evidence is the captured DOM of the real application executed in
   jsdom plus live dev-server HTTP probes.
2. The jsdom run uses a development-mode build of the same sources the dev server serves; it is
   equivalent in module graph but is not literally the browser rendering the dev server output.
3. Everything demonstrated is synthetic. No Dhan credential, authentication, connectivity,
   coverage, latency or streaming behaviour is proven, and every ACCESS-PENDING item in
   `docs/DHAN-D2-INTEGRATION-QUALIFICATION.md` remains open.
